# Объектив: дизайн фронта (первый проход)

Дата: 16 сентября 2026. Статус: согласован продактом, готов к плану реализации.
Основа: макет «Сборка Объектива 0.4», ТЗ MVP v1.1 от 10.09.2026, ТЗ организаторов (15.09.2026), созвон команды 16.09.2026.

## 1. Зачем и в каких границах

Фронт собирается первым, до бэкенда. Он должен работать по публичной ссылке без сервера и показывать все четыре обязательные функции ТЗ организаторов: детекцию техники на снимках, сопоставление «этап → техника», визуализацию, выявление отклонений двух типов (нужной техники нет; появилась техника, не соответствующая этапу).

Решения созвона 16.09:

- Авторизации, ролей и уведомлений нет.
- Загрузка календарного плана через интерфейс есть.
- Пример плана от организаторов и формат сдачи прототипа (ссылка или Docker) ждут ответа. Дизайн закрывает оба исхода: свой синтетический план на основе справочника организаторов, статический экспорт для ссылки плюс Dockerfile.

Кодим все четыре экрана макета 0.4 в объёме макета, без новых функций: Портфель, Разбор работы, Камера, Настройка. Портфель и контакты шире ТЗ MVP; это осознанное решение продакта.

Не входит в первый проход: бэкенд и API (задание Георгию после фронта), языковая модель для импорта и вердиктов (надстройки, требуют сервер-посредник), re-ID техники между камерами, мобильное приложение прораба.

## 2. Стек и репозиторий

- Next.js + React + TypeScript, статический экспорт (`output: 'export'`). Графики: Recharts или свои SVG, как в макете.
- Репозиторий `jas76123/obyektiv` на GitHub; структура: `frontend/` (фронт), `backend/` (позже, Георгий), `docs/`, `data/`. Позже перенос в SourceCraft по требованию организаторов; git-история переносится целиком.
- Коммиты от имени Жасмины, без упоминаний ИИ-инструментов.
- Выкладка: Vercel или GitHub Pages для ссылки; `frontend/Dockerfile`, который отдаёт ту же папку экспорта.

## 3. Архитектура: три слоя

**Данные.** `frontend/data/`: файлы-заглушки строго в формате контракта (раздел 4). Один объект, ЖК «Северный» к.2, камера 1, собирается из реального JSON Георгия (`analysis/2026-09-16-video_detections_tracked.json`: кадры, `time_sec`, `bbox`, `id` трека). Остальные пять объектов портфеля — синтетика из макета 0.4, помеченная в коде как демо.

**Слой доступа.** Один модуль `api.ts`: функции «сводка объекта на дату», «разбор работы», «снимки камеры за смену», «настройка объекта». Внутри переключатель источника: файлы или сервер (`NEXT_PUBLIC_API_BASE`). Экраны источника не знают.

**Экраны и компоненты.** Четыре страницы. Общие компоненты: чип статуса, триада процентов (план / заявлено / подтверждено), календарь дней, снимок с рамками, карточка «требует внимания», Гант.

**Мозг v0** (`engine/`): нужен уже в первом проходе, потому что импорт плана обязан пересчитывать экраны. Правило: для каждой работы на каждый рабочий день этапа берём снимки камер её зоны. Нужная по справочнику техника на снимках есть → уровень 1 «ресурсы на месте»; есть и меняет положение между снимками → уровень 2 «работа идёт»; нет → 0. Из уровней по дням и заявленного факта складывается один из семи статусов ТЗ MVP. Пороги (доля дней, порог покрытия, порог уверенности 0.5) лежат в одном файле констант и уточняются БА. Отклонения ТЗ организаторов: «нужной техники нет» = уровень 0 при плане; «чужая техника» = класс на снимке, которого нет в справочнике ни у одной работы этой зоны на дату.

Когда появится бэкенд, мозг переезжает на сервер; контракт не меняется.

## 4. Контракт данных

Оформляется как TypeScript-типы в `frontend/contract/` плюс примеры JSON. Тот же файл идёт Георгию как описание модели данных для документации (раздел 5 ТЗ организаторов).

Сущности:

- Объект → зоны → камеры; камера привязана к одной зоне.
- Работа плана: id, название, зона, подрядчик, план начала и конца, заявленный факт %.
- Правило справочника: вид работ → классы техники с минимумом, минимум людей, порог дней.
- Снимок: камера, время, файл картинки, список детекций.
- Детекция: класс, уверенность, рамка `[x, y, w, h]`, id трека. Формат JSON Георгия от 16.09 плюс камера и время снимка.

Четыре ответа, все с параметром «дата среза»:

1. Сводка объекта: счётчики; работы с планом, фактом и статусом для Ганта; карточки «требует внимания» с текстом «что не так» и одним снимком-основанием; состояние камер.
2. Разбор работы: лестница подтверждения; таблица ожидалось / обнаружено; уровень по дням; вердикт; гипотезы причин; история правок плана; снимки-основания.
3. Снимки камеры за смену: список снимков с детекциями и связью с планом («в этой зоне сейчас должна идти W-02»).
4. Настройка: источник плана, камеры с зонами, справочник, контакты подрядчиков.

Портфель = список сводок по объектам, отдельного ответа нет.

Правила контракта:

- Классы техники в терминах ТЗ организаторов (самосвал, экскаватор, каток, кран-манипулятор, бетоносмеситель, бульдозер, грузовик, автокран, плюс человек). Названия модели («Bucket loader Standart», «Tanker», «Mixer») переводятся в них один раз, в слое данных, таблицей соответствия.
- Статусы работ — семь из ТЗ MVP, текстом; цвет выбирает фронт.

## 5. Загрузка плана

На экране «Настройка»: пользователь выбирает CSV или XLSX → фронт показывает колонки файла и наши обязательные поля (id, название, зона, подрядчик, план начала, план конца, факт %) → пользователь связывает их выпадающими списками и подтверждает → проверка: нет обязательной колонки — импорт отклонён целиком, колонка названа → успех: «загружено N работ, M не найдено в справочнике» → план сохраняется в браузере, все экраны пересчитываются мозгом v0.

Языковая модель как надстройка второго шага: автоматически предлагает связывание колонок и сопоставление названий работ со справочником, пользователь только проверяет. Требует сервер-посредник (ключ нельзя держать в браузере); идёт в задачи бэкенда.

## 6. Обработка карточки и «Написать»

Текст обращения собирается автоматически из данных карточки: работа, зона, объект, заявленный факт, что зафиксировала камера и за какие дни, просьба, упоминание снимка-основания. Пользователь ничего не заполняет, при желании правит.

Кнопки по порядку: Макс, Telegram, почта, «Скопировать текст». Telegram и почта открывают чат с готовым текстом по ссылке. Для Макса при реализации проверить, есть ли ссылка с готовым текстом; если нет, кнопка открывает чат с контактом, текст автоматически копируется в буфер. После нажатия карточка переходит в состояние «связались»; состояния обработки (новая / увидел / связался / закрыто с исходом) хранятся в браузере.

Контакты подрядчиков лежат в файле настройки объекта. Если контакта нет, карточка показывает «ответственный от подрядчика не указан» и поле добавить контакт (имя, телефон, Telegram/Макс), сохраняемое в браузере и подставляемое в следующие карточки того же подрядчика.

## 7. Вердикты и тексты

Мозг выдаёт факты структурой (ожидалось, найдено, дни, порог). Тексты вердиктов, «что не так» и гипотез причин собираются по шаблонам, как в макете. Языковая модель как надстройка: переформулирует факты по жёсткой инструкции без добавления фактов, тексты для демо генерируются заранее. Для презентации: сверка детерминированная и проверяемая, модель только для удобства ввода и читаемости.

## 8. Граничные случаи

По таблице ТЗ MVP, каждый с текстом на экране: нет снимков за день (уровень null, день вне знаменателя, «нет данных»); выходной или праздник (штриховка, не простой); снимков меньше порога покрытия (not_checked · no_frames); работа не найдена в справочнике (not_checked · no_catalog, список после импорта); работа без наблюдаемой техники (not_checked · no_observable); на зоне нет камеры; камера не привязана к зоне; детекция ниже 0.5 не засчитана и не рисуется; файл плана без обязательной колонки отклонён.

## 9. Проверка

- Мозг v0: юнит-тесты по приёмочной таблице `data/demo`: на демо-данных ровно те карточки и статусы, что в таблице.
- Импорт: тесты на отклонение файла без колонки и на подсчёт «не найдено в справочнике».
- Экраны: ручная проверка на ширине телефона (около 400px) и ноутбука; статусы читаются без цвета.
